三、代码示例

下面是一段 Swift 代码：

func scrollToBottom() {
    let contentHeight = textView.contentSize.height
    let visibleHeight = textView.bounds.height
    let offsetY = max(
        -textView.adjustedContentInset.top,
        contentHeight - visibleHeight
    )
    textView.setContentOffset(
        CGPoint(
            x: textView.contentOffset.x,
            y: offsetY
        ),
        animated: false
    )
}

在实际项目中，如果文本内容包含异步加载的图片，那么图片加载完成后可能会导致 contentSize 再次发生变化，因此通常需要重新执行布局和滚动逻辑。

十、长文本测试

在实际项目中，文本内容往往不会只有几行。尤其是在 AI 对话、文章阅读、知识问答等场景中，一条消息可能包含大量连续文本。

当文本数量增加之后，布局性能就会变得越来越重要。如果每次新增几个字符都重新创建完整的 NSAttributedString，然后重新计算整个文本布局，那么随着文本长度增加，可能出现越来越明显的卡顿。

一种常见的优化思路是将文本拆分成多个阶段进行处理：首先接收原始字符串，然后解析新增内容，再将已经确定的 Markdown 内容转换成富文本。对于仍然可能发生变化的 Markdown 片段，则暂时保留到下一次数据到达后再继续解析。

这种方式尤其适合流式数据。

例如服务器持续返回：

今
今天
今天是
今天是一个
今天是一个阳
今天是一个阳光
今天是一个阳光明媚
今天是一个阳光明媚的
今天是一个阳光明媚的日子。

如果每次都重新解析全部内容，会产生大量重复工作。

更合理的方式是：

1. 保存已经提交的文本。
2. 找到一个安全的 Markdown 提交位置。
3. 只解析已经确定不会变化的部分。
4. 暂时保留未完成的 Markdown 结构。
5. 下一批数据到达后继续处理。

这种设计能够减少重复解析，同时降低文本布局压力。

十一、综合测试

最后，再使用一段混合格式文本进行测试。

Markdown 是一种简单而强大的文本标记语言。 它可以使用标题组织文章结构，也可以使用列表表达多个项目，还可以通过代码块展示程序代码。

在设计 Markdown 渲染器时，真正困难的部分往往不是解析语法，而是如何将解析结果稳定、高效地转换成最终的 UI。

例如，一个段落中可能同时存在粗体、斜体、代码、链接以及图片。

当这些内容同时出现时，渲染器需要正确处理字体、颜色、段落间距、行高、点击事件和附件布局。

如果再加入表格、公式、代码块和异步图片，那么整个文本系统实际上已经变成一个比较完整的排版引擎。

因此，一个好的 Markdown 组件应该不仅能够“显示出来”，还应该做到：

* 内容结构正确；
* 排版稳定；
* 滚动流畅；
* 图片加载不会导致明显跳动；
* 长文本不会出现严重卡顿；
* 用户滚动位置能够得到尊重；
* 异步内容更新后能够正确刷新布局。

最终目标不是让 Markdown 看起来复杂，而是让复杂的 Markdown 在用户眼中看起来足够简单。
